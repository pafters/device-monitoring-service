# Описание бизнес-логики сервиса мониторинга состояния устройств

## Глоссарий
1. **Валидное устройство** - Устройство считается валидными, если оно соответствует всем следующим пунктам:
    1. Устройство добавлено в таблицу "devices". 
    2. У устройства в таблице "devices" заполнены поля: server_alias_template_id, location_id, model_id.
    3. У устройства с указанным location_id существует локация в таблице "locations".
    4. У локации, к которой привязано устройство, заполнено поле site_id.
    5. У устройства есть связка с модемом в таблице server_modem_device_binds.
    6. Указанный в связке (server_modem_device_binds) модем существует в таблице "modems".


## База данных

### Таблица alarm_configurations
Таблица конфигураций, по которым параметры должны соответствовать для срабатывавния или завершения того или иного типа аларма.
* alarm_config_id - Уникальный идентификатор записи конфигурации в таблице alarm_configurations.
* alias - Параметр, по которому нужно провести проверку.
* activation_condition - Проверяемое тождество на активацию аларма. Например "Больше или равно значению". 
* activation_condition_value - Проверяемое значение на активацию аларма.
* activation_condition_time_to_activate_ms - Время в милисекундах, сколько должно сохраняться значение по алиасу, на то, чтобы активировать аларм. Поле необязательно к заполнению, если ждать для активации аларма не нужно - в поле указывается значение 0.
* finish_condition - Проверяемое тождество на завершение аларма. Например "Больше или равно значению". Поле необязательно к заполнению. Если поле не заполнять, то завершением аларма считается невыполнение условия, указанное в поле activation_condition.
* finish_condition_value - Проверяемое значение на завершение аларма.
* finish_condition_time_to_activate_ms - Время в милисекундах, сколько должно сохраняться значение по алиасу, на то, чтобы завершить аларм. Поле необязательно к заполнению, если ждать для завершения аларма не нужно - в поле указывается значение 0.
* alarm_level - Тип аларма. Например "Предупредительный".
* alarm_activation_text - Текст активации, который будет показываться пользователю в момент срабатывания аларма.
* finish_without_acknowledgement - Требуется ли квитирование пользователя после завершения аларма. Если требуется, то запись о завершенном аларме попадает в таблицу "alarm_finished_alarm_await_confirmation". Если квитирование от пользователя не требуется, то запись о завершении аларма попадает в таблицу "alarm_finished_alarms".
* deleted_at - В положительном сценарии запись конфигурации из таблицы физически не удаляется. Она остается в таблице и имеет метку deleted_at с датой ее "удаления".

### Таблица alarm_configuration_binds
Таблица связок конфигурации и критериев по которым разрешается проверить эту конфигурацию на алармы. Под критериям понимается проверяемые по конфигурации устройство, шаблон параметра переменных сервера, модель устройства, локация, организация. Например конфигурацию с alarm_config_id = 1 проверять для всех устройств у которых model_id = 108.
При создании связки необходимо заполнить хотя бы одно поле из всех критериев. 

* alarm_configuration_binds_id - Уникальный идентификатор таблицы связок.
* alarm_config_id - Уникальный идентификатор конфигурации, по которой проводить проверку.
* device_id - Уникальный идентификатор устройства.
* server_alias_template_id - Уникальный идентификатор шаблона параметров переменных сервера.
* model_id - Уникальный идентификатор модели устройства.
* location_id - Уникальный идентификатор локации.
* site_id - Уникальный идентификатор организации.

> Если разобрать более сложную связку, в которой заполнены поля alarm_config_id = 9, device_id (например значением 1508), model_id = 108 и site_id = 22 - Это значит, что указанная конфигурация по уникальным индентификатором 9 будет проверяться только в случае, если у устройства с device_id=1508 будет находиться в организации с id = 22 и модель этого устройства соответствует модели с id = 108.

### Таблица alarm_configuration_blacklist_binds
Таблица связок конфигурации и критериев, по которым запрещается проверять конфигурацию на алармы. Под критериям понимается проверяемые по конфигурации устройство, шаблон параметра переменных сервера, модель устройства, локация, организация. Например конфигурацию с alarm_config_id = 1 нельзя проверять для всех устройств у которых model_id = 108.
При создании связки необходимо заполнить хотя бы одно поле из всех критериев. 

* alarm_configuration_blacklist_binds_id - Уникальный идентификатор таблицы связок.
* alarm_config_id - Уникальный идентификатор конфигурации, по которой проводить проверку.
* device_id - Уникальный идентификатор устройства.
* server_alias_template_id - Уникальный идентификатор шаблона параметров переменных сервера.
* model_id - Уникальный идентификатор модели устройства.
* location_id - Уникальный идентификатор локации.
* site_id - Уникальный идентификатор организации.

> Если разобрать более сложную связку, в которой заполнены поля alarm_config_id = 9, device_id (например значением 1508), model_id = 108 и site_id = 22 - Это значит, что указанная конфигурация по уникальным индентификатором 9 не должна будет проверяться только в случае, если у устройства с device_id=1508 будет находиться в организации с id = 22 и модель этого устройства соответствует модели с id = 108.

### Таблица alarm_active_alarms
Таблица активных алармов. В позитивном сценарии дубликатов по ключам alarm_config_id + device_id - не должно быть. Одно устройство может иметь только один активный аларм по конфигурации.

* alarm_activation_guid - Уникальный идентификатор таблицы активных алармов.
* alarm_config_id - Уникальный идентификатор конфигурации.
* device_id - Уникальный идентификатор, по которому активировался аларм.
* dt_start - Дата и время активации аларма.
* activation_value - Значение по алиасу в момент активации аларма.
* debug_info - Отладочные данные по аларму

### Таблица alarm_finished_alarms
Таблица завершенных алармов. В таблицу попадают завершившиеся алармы, не требующие от пользователя квитирования либо квитированные завершившиеся алармы.

* alarm_activation_guid - Уникальный идентификатор аларма (равен уникальному идентификатору, который формируется, когда аларм активируется).
* alarm_config_id - Уникальный идентификатор конфигурации, по которому был активирован аларм.
* device_id - Уникальный идентификатор устройства, по которому был активирован аларм.
* dt_start - Время активации аларма (указывается время, когда сервис зафиксировал значение, подлежащее активации аларма).
* activation_value - Значение по алиасу в момент активации аларма.
* dt_end - Время завершения аларма (указывается время, когда сервис отнес активный аларм к завершенным).
* finish_reason - Причина завершения аларма.
* debug_info - Отладочные данные по аларму.

### Таблица alarm_finished_alarms_await_confirmation
Таблица завершенных алармов, ожидающих квитирования пользователем. В нее попадают завершенные алармы, по которым еще нет записи в таблице квитирований alarm_user_acknowledgement. При квитировании аларма запись из таблицы alarm_finished_alarms_await_confirmation переносится в alarm_finished_alarms с помощью вспомогательных методов на бэкенде (если аларм уже находится в завершенных) либо с помощью методов сервиса алармов 2.0., если аларм квитировали пока он был еще активным.

* alarm_activation_guid - Уникальный идентификатор аларма (равен уникальному идентификатору, который формируется, когда аларм активируется).
* alarm_config_id - Уникальный идентификатор конфигурации, по которому был активирован аларм.
* device_id - Уникальный идентификатор устройства, по которому был активирован аларм.
* dt_start - Время активации аларма (указывается время, когда сервис зафиксировал значение, подлежащее активации аларма).
* activation_value - Значение по алиасу в момент активации аларма.
* dt_end - Время завершения аларма (указывается время, когда сервис отнес активный аларм к завершенным).
* finish_reason - Причина завершения аларма.
* debug_info - Отладочные данные по аларму.

### Таблица alarm_user_acknowledgement
Таблица квитирований. В ней отмечается какой аларм и кем был квитирован.

* alarm_activation_guid - Уникальный идентификатор аларма, который квитировали
* user_id - Уникальный идентификатор пользователя, кто квитировал аларм.
* user_commnet - Комментарий, который оставил пользователь после квитирования. Необязателен к заполнению.
* alarm_user_acknowledgement_id - Уникальный идентификатор записи таблицы квитирований.


## Формирование конфигураций

### Поля activation_condition и finish_condition
Тождество по которому сверять оперативное значение по датчику со значением в конфигурации 
* larger_or_equal (Больше или равно)
* larger_not_equal (Больше)
* less_or_equal (Меньше или равно)
* less_not_equal (Меньше)
* equal (Равно)
* not_equal (Неравно)
* in_array (Соотвествует значению в массиве)
* not_in_array (Соответствует значению, который не указан в массиве)

### Поля activation_condition_value и finish_condition_value
Для типов **"larger_or_equal"**, **"larger_not_equal"**, **"less_or_equal"**, **"less_not_equal"**, **"equal"**, **"not_equal"** полей таблицы **"activation_condition"** и **"finish_condition"** ожидается следующая передача значений в поля "activation_condition_value" и "finish_condition_value":
* Текстовое значение (Например: #Стоп, ОК).
* Числовое значение (Напимер: 1, 15.56).
* Булевое значение (Например: true, false).

Для типов **"in_array"** и **"not_in_array"** ожидается следующая передача значений в поля:
* Одномерный массив чисел, строк, булевых значений (Напимер [125.45, 10], [true], ['#СТОП', " ОК"])

## Особенности определения связок подлежащих проверке по устройству: Формирование связки проверок и связки исключения из проверок
В таблице связок проверок "alarm_configuration_binds" указываются все возможные связки, по которым должны проводиться проверки. Указанные в связках значения необязательно должны удовлетворять текущим особенностям устройства. Приведу пример: Если у нас устройство (device_id = 201) находится в организации с id = 22. В таблице "alarm_configuration_binds" может быть связка с id другой организации. Например связка: alarm_config_id=10, device_id=201, site_id=5, model_id=null, location_id=null, server_alias_template_id=null. Для такой связки проверка будет выполняться тогда и только тогда, когда устройство с device_id = 201 будет находиться в организации с id = 5.

С таблицей исключений из проверок все так же. Если в таблице исключений из проверок будет указано alarm_config_id=10, device_id=201 и site_id=22. То указанная конфигурация будет исключена из проверок тогда и только тогда, когда устройство будет расположено в организации с id = 22.

При формировании связки по локации нужно учитывать, что связка будет распространяться как на указанную локацию в поле location_id, так и на все ее дочерние локации. То есть, если устройство находится по пути из локаций "ESP/ Казах Ойл Актобе/ KOA/ Alibekmola/ 104/", а в связке под проверки указывается локация "KOA", то это устройство будет так же проверено, так как в его полном пути указана эта локация.

Чтобы исключить из проверок это устройство, то в список исключений можно например указать либо одну из локаций, в которой находится это устройство (Например "Alibekmola"), либо само устройство. В первом случае если указать только локацию "Alibekmola", а остальные поля в связке исключения не заполнять, то все устройства, что находятся в этой 
локации будут так же исключены из проверки, указанной для "КОА" и ее дочерних

## Принцип работы сервиса
### Первый запуск приложения
1. **Проверка активных алармов на завершение по причине несоответствия со статическими данными** -
    
    Активный аларм можно считать недействительным и подлежащим к завершению, если по нему выполняется хотя бы одно из следующих условий: 
    1. Устройство удалено.
    2. Устройство больше не соответствует связке и конфигурации по которой открывался аларм.
    3. Конфигурация находится в списке исключений из проверок для этого устройства.
    4. Конфигурация удалена.
    5. Устройство больше не связано с модемом в таблице server_modem_device_binds.
    6. Конфигурация больше не соответствует параметру, по которому был активирован аларм (Т.е. в конфигурации был изменено поле alias на другое значение).

2. **Проверка по значениям параметров из оперативных данных всех валидных устройств на активацию алармов либо завершение уже существующих алармов**


### Работа сервиса после выполнения процедур первого запуска
1. **Проверка активных алармов на завершение по причине невалидности статических данных** - проводится раз в N-интервал, указанный в настройках enveronment файла. 
2. **Проверка на активацию алармов или завершение уже активных по поступающим в Valkey значениям** - Проверка проходит по всем подлежащим проверке конфигурациям удовлетворяющим устройству и параметру, по которым поступило значение. 

    **!Заметка:** Если в Valkey поступило значение по параметру, относящемуся к шаблону параметров модема, например "Modem_link", и ключ Valkey начинается с "modem/", то система должна обработать все устройства, к которым привязан этот модем в таблице 

## Жизненный цикл аларма
### Перманентая активация

Активация аларма срабатывает сразу при фиксировании значения в оперативных данных, если:
1. Значение из оперативных данных удовлетворяющее тождеству и значению для активации аларма (поля "activation_condtion" и "activation_condition_value").
2. Устройство заведено в систему и считается валидным*.
3. Поле activation_condition_time_to_activate_ms заполнено значением 0, чтобы аларм активировался сразу.
4. В систему еще не заведен активный аларм для таких конфигурации и устройства.

 
### Отложенная активация

Отложенная активация запускается в момент, когда система фиксирует в оперативных данных первое удовлетворяющее условиям активации аларма значение по параметру.

Полноценная активация срабатывает сразу после того как пройдет время, указанное в поле "activation_condition_time_to_activate_ms", при условии, что за указанное время значение по параметру в оперативных данных выполняет условия активации.

Отложенная активация отменяется, если выполняется хотя бы одно из следующих условий:
1. Значение в оперативных данных по параметру в момент отложенной активации возвращается к тем значениям, при которых аларм не может считаться активным (т.е. значение по параметру вернулось в норму).
2. Конфигурация и устройство, по которым происходит отложенная активация, уже находится в списках активных алармов.
3. Устройство удалено.
4. Устройство больше не соответствует связке и конфигурации по которой открывался аларм.
5. Конфигурация и устройство, по которым происходит отложенная активация уже находятся в списках активных алармов.
6. Конфигурация находится в списке исключений из проверок для этого устройства.
7. Устройство больше не связано с модемом в таблице server_modem_device_binds.
8. Конфигурация больше не соответствует параметру, по которому был активирован аларм (Т.е. в конфигурации было изменено поле alias на другое значение).

### Перманентное завершение

Завершение аларма сразу при фиксировании причины, подлежащей завершению аларма.
Аларм может перманентно завершиться, если удовлетворяет хотя бы одному из следующих условий:
1. Конфигурация удалена.
2. Устройство удалено.
3. Устройство больше не соответствует связке и конфигурации по которой открывался аларм.
4. Конфигурация находится в списке исключений из проверок для этого устройства.
5. Устройство больше не связано с модемом в таблице server_modem_device_binds.
6. В настройках конфигурации не указано отложенное завершение.
7. Конфигурация больше не соответствует параметру, по которому был активирован аларм (Т.е. в конфигурации был изменено поле alias на другое значение).
8. Аларм, по которому происходит завершение находится в списке активных алармов.
9. Аларм, по которому происходит завершение еще не находится в списке завершенных алармов.

### Отложенное завершение

Отложенное завершение запускается в момент, когда система фиксирует в оперативных данных первое удовлетворяющее условиям завершения аларма значение по параметру.

Полоценное завершение срабатывает сразу после того как пройдет время, указанное в поле "finish_condition_time_to_activate_ms", при условии, что за указанное время значение по параметру в оперативных данных продолжает соответствовать установленным условиям для завершения (это может быть условия завершения, указанные в соответствующих полях либо если эти поля не были заполнены, то завершением можно считать невыполнение условиям активации аларма).

Отложенное завершение отменяется, если выполняется хотя бы одно из следующих условий:
1. Значение в оперативных данных по параметру в момент отложенного завершения возвращается к тем значениям, при которых аларм считается активным.
2. Конфигурация и устройство, по которым происходит отложенная активация, уже находится в списках активных алармов.
3. Устройство удалено.
4. Устройство больше не соответствует связке и конфигурации по которой открывался аларм.
5. Активный аларм, по которому происходит отложенное заверешние уже был завершен или больше не существует.
6. Конфигурация находится в списке исключений из проверок для этого устройства.
7. Устройство больше не связано с модемом в таблице server_modem_device_binds.
8. Конфигурация больше не соответствует параметру, по которому был активирован аларм (Т.е. в конфигурации было изменено поле alias на другое значение).
